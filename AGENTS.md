# Project agent instructions

## 协作与交付

- **表达清楚。** 先给结论，再说明依据。沿用用户和项目资料中的术语，用主动语态，保留理解问题所需的技术细节。
- **最终回复可以独立阅读。** 写清完成了什么、验证结果和仍待确认的事项。补足读者理解结果所需的背景，避免引用只有在进度更新、工具输出或内部讨论中才看得懂的简称。
- **在授权范围内做到交付。** 用户要求执行时，主动完成后续操作和相关检查，处理可恢复的失败。结束前对照请求和验收标准逐项核对，说明仍未完成或未验证的部分。
- **对可撤销的小决定自行判断。** 信息不足时，可在已确认的范围内作合理且可撤销的假设，交付时说明影响结果的假设。产品和交互决策按既有流程由用户确认。遇到重大范围变化、必须由用户决定的事项、无法自行解除的阻塞，或需执行破坏性或不可逆操作时，先确认相关事项，并继续推进不依赖该决定的工作。

## Genkit Dart architecture requirements

- For changes to Agent execution, tool loops, streaming, conversation state, cancellation/resumption, or branching, first read the project's `developing-genkit-dart` skill and verify both client/server lockfiles and the resolved SDK sources. Use the installed Dart version as the implementation authority; do not substitute another language's API or a newer version's documentation. If documentation redirects to another version, state that and inspect the matching published source.
- Before implementation, record a capability mapping: **requirement → official API and version-specific source → existing integration → reuse / adapt / remove → concrete missing capability → state owner**. Not having found an API is not evidence that the SDK lacks it. Resolve uncertainties before implementing a replacement. Keep this mapping with the development plan and review the actual diff against it.
- Ordinary chat must use the standard Genkit Agent model/tool loop and official message, stream, session, snapshot and branching contracts. Do not add mandatory classification, preparation, planner/executor or final-answer model stages merely to hide tool preambles, format output or normalize wording. Prompt text must not be used as a substitute for runtime state or protocol guarantees.
- Prefer official extension points (`SessionStore`, model plugins, middleware, `defineTool`, MCP and skills integrations) for Xiaoqi-specific requirements. Custom code is limited to confirmed business requirements or a demonstrated SDK/provider gap. Each exception must identify why the official capability is insufficient, its input/output, state owner, bounded scope and replacement/removal condition. Do not implement another model/tool loop or parallel execution-history/snapshot authority inside an adapter. Do not ban `defineCustomAgent` or `generate` by name: inspect their purpose and whether a standard path already covers it.
- Distinguish cancellation recovery, tool-interrupt `respond`/`restart`, answer continuation, and regeneration by branching. Verify the installed SDK's checkpoint semantics; never claim a partial streamed answer or provider KV state is automatically resumable. Reuse existing operation journals for external effects, verify unknown results before retrying, and retain account isolation, permissions, capability-version binding, user history and book associations.
- Keep prompt prefixes and tool-definition ordering stable where practical; append changing task data after stable instructions. Do not invent a local KV-cache system or claim cache-hit improvements without provider usage evidence. Keep raw model content, tool execution records and UI presentation separate in responsibility without introducing competing execution-state owners.
- For Flutter A2UI, verify the protocol version emitted by the installed `genkit_a2ui` package and use the matching official `a2ui_core` `MessageProcessor` and `a2ui_flutter` `A2uiSurface` APIs. If the official modular Flutter packages replace/deprecate `genui`, migrate to them; do not keep the deprecated renderer or hand-roll protocol parsing, surface state, or action serialization. Product-specific controls may be implemented as official catalog components and must dispatch actions through the A2UI surface API.
- Before handing off an Agent change, report the capability mapping, any justified exceptions, and evidence for the affected cancellation/recovery, branching and tool identity behavior. Code compilation or tests passing alone do not establish architecture compliance. Any new model phase, execution-history owner or recovery mechanism that departs from the confirmed architecture requires updating the plan and explaining the deviation before implementing it. A previously documented deficiency is not approval to silently weaken the user's requested behavior.
- Reference baseline: `docs/diagnostics/2026-11-15-genkit-1.0-reuse-repair-plan.md`. Recheck its version-dependent statements when dependencies change. These are mandatory design/review requirements; they do not imply that an automated architecture gate is already installed, and they do not authorize implementation when the user requested discussion only.

## 日常运行与 Agent 调试工作流

日常运行 Flutter 客户端与调试 Genkit 服务端是不同操作。启动 App 使用项目根目录的 `./flutterw.cmd run`（项目 Flutter 包装入口）。排查 Agent、工具、技能/插件、流式、停止/继续/重新生成时，默认只启动本地服务和 Genkit Developer UI；不启动 Flutter App，也不要求用户先操作平板。只有问题明确属于 Flutter 展示/客户端状态/平台行为，或用户明确要求客户端/真机验收时，才启动 App。

### 固定调试顺序

1. **先核对运行目标与隔离边界。** 看当前 Genkit CLI/SDK 锁定版本、端口、模型配置和本地数据目录；不为 Agent 链路问题先查或启动 Android 设备。先看 `git status`，不覆盖用户已有改动。测试数据默认写入本地隔离目录，不接生产数据，不把密钥放入 Flow 输入、Trace 或命令输出。
2. **启动小栖 Agent 测试 Flow 和 Developer UI。** 在项目根目录运行 `./tools/start_genkit_devtools.ps1`，入口为 `xiaoqi_harness/genkit_server/tool/genkit_devtools_agent.dart`。它提供本地合成身份和真实的 `/v1/agent/chat` 请求上下文，执行同一条小栖 Agent/工具链；这只用于本地诊断，不是生产认证或权限绕过。Developer UI 的“代理人”直连页不会自动带小栖的租户身份及 `xiaoqi_agent_turn` 元数据，不能用它代表业务 Agent 测试；需运行 `xiaoqi_agent_dev_test` Flow。普通请求和工具请求可在 Flow 中复现；Genkit Developer UI 的 Flow 运行面板没有单独的停止按钮，停止恢复通过 Flow 的本地调试参数 `cancel_after_ms` 触发相同任务取消 API，再用输出的 `resume_input` 从 snapshot 继续。重新生成/后续问题用 `branch_input` 验证分支。
   - 本地启动脚本将 `XIAOQI_CAPTURE_TRACES=0`，只让 API 与 DevTools Flow 注册 reflection runtime；Genkit CLI 在 Flow runtime 上触发 Evaluation。不要改回 `1`：每个请求临时创建的 Agent Genkit 会各自启动 reflection runtime，CLI 的 `eval:flow` 又按最近 runtime 查找 Flow，导致 Evaluation 报 `Cannot find action`。Genkit instrumentation 仍由 Dev 环境提供，Trace 中保留内层 Agent span。
3. **用一条明确场景复现。** 在 Flow 页输入问题，只测试一条目标路径。新对话、取消/继续、工具中断恢复和重新生成/分支需区分操作，保留 task、session、snapshot、attempt、模型和操作次序。涉及重复调用的状态用 Flow 输出的官方 snapshot/session 标识复现，不另建执行历史作为权威。
4. **在 Traces 逐 Span 定位。** 打开 CLI 提示的 Developer UI（通常 `http://localhost:4000`），先从 Flow 的 Trace 打开 Agent 子步骤，再检查模型真实输入、工具定义/参数、工具结果、后续模型调用、耗时和错误。使用 `genkit trace:list` 和 `genkit trace:get <traceId> --format json` 导出本地证据。检查具体 finishReason、snapshot 和业务任务状态；Trace 绿灯或 UI 文案本身不能证明业务成功。
5. **必要时建立 Evaluation Dataset。** 使用 Developer UI 的 Datasets 创建 Flow 类型数据集，保存可重复的普通对话、应触发工具、工具失败、技能/插件选择等输入；对比时确认目标 Flow、模型和能力安装状态相同。评估没有自动指标时先人工检查输出和 Trace。合成租户没有安装的技能/插件，不能靠提示词或评估结果宣称真实账号能力可用；应明确报告测试 Fixture、账号安装版本和权限范围。
6. **只有客户端问题才启动 App。** Flutter 界面状态、客户端事件处理、网络切换或平台问题确需复现时，再检查设备并由用户选择目标 serial；用 `adb reverse` 和 `CAPABILITIES_BASE_URL` 指向本地服务。设备验证与 Developer UI 后端验证分别记录，不能互相代替。

### 使用边界与职责

- **CLI** 负责启动、运行、查询和导出；**Developer UI** 用于交互式 Flow 试跑、数据集评估与 Trace 可视化。只运行 `genkit start` 而不带应用启动命令，不能代表业务后端已接通。Agent 链路问题默认用本地 DevTools Agent Flow，不启动 Flutter App。
- Trace 反映实际被接入采集的 Genkit 执行链，不自动包含所有 Flutter 状态、所有服务器日志、模型未返回的内部思考或 SDK 之后由 HTTP 适配器修改的最终请求字段。必要时关联官方 snapshot、任务/副作用记录和经过脱敏的请求边界信息；不得另建一套执行历史权威。
- 技能/插件验收应区分宿主加载正文、模型选择技能、命令/脚本执行和 MCP 调用，并核实当前账号安装版本、选择与权限。模拟模型的 Trace 只能证明对应本地调用路径；UI 的“使用技能”提示不能独立证明模型实际调用或真实任务交付成功。
- Agent 负责准备命令、检查版本、启动本地服务和分析证据；Agent 链路调试不要求用户先操作 App 或设备。指导用户查看仪表盘时一次给一个可执行步骤并说明当前进度。仅需正常运行客户端时，不强制启动本地后端或仪表盘。
- 本地调试不替代既有发布流程；仅文档或诊断准备无需部署，涉及生产服务代码/API 行为修改时继续遵守下方部署规则。Trace 和凭据只保存在合适的本地私有位置；不把未经检查的原始 Trace 提交到仓库或公开分享。

## Single-version development policy

- During the solo-development stage, maintain one current product version. Treat the Flutter client, server code, API contract, and ECS deployment as one release rather than as independently managed versions.
- Every release must carry a shared release identifier and API contract version. Before normal API use, the client and server must verify that their contract versions match; on mismatch, stop the affected flow and show both versions with a clear instruction to rebuild the client or redeploy the server.
- When a client-server contract changes, update and verify both sides in the same task. Do not add legacy-client compatibility or preserve old request formats unless the user explicitly requests it.
- Run only the current release. Keep at most one non-running emergency restore point, replace it after each successful deployment, and remove all older images, tags, backups, staging uploads, and temporary files after health and data checks pass.
- The user is responsible for product decisions and client verification. The agent is responsible for version matching, server deployment, health and data checks, automatic rollback on failure, cleanup, and a plain-language report of what actually succeeded.

## Remote service deployment

### Validated scope and reuse defaults

- Follow `docs/architecture/release-flow-validation-2026-11-05.md` and `xiaoqi_harness/deploy/README.docker.md`. The full baseline, Linux isolated recovery, production activation and a four-component reuse run were verified on 2026-11-05. Use the existing workflow and deployment entry point for future releases.
- Select checks against the latest successful main whose workflow supports cumulative checking, not merely the previous commit. Failed or cancelled runs do not erase unverified changes. Bootstrap a new checking policy with a complete baseline.
- Reuse only verified images whose component input and base-image fingerprints match. Preserve actual component source commits and image IDs; build only changed or missing components. A release artifact still belongs to the exact current main, and image export/import verification remains mandatory. Scope business probes to affected behavior while keeping backup, health, contract, data verification and rollback for every actual activation.
- Official capability sources and releases live in `Yseven004/xiaoqi-capabilities`; package-only updates do not rebuild or deploy the host. Package installation/update is manual. Preserve installed history and versions bound to active work; the product's single-version cleanup policy must not delete capability versions referenced by work. A package version switch never rewinds user data or grants permissions.

- During solo development, deployment is the agent's automatic responsibility, not a manual user step. After changing production server code under `xiaoqi_harness/genkit_server/`, runtime deployment files under `xiaoqi_harness/deploy/`, or a Flutter/server API contract, the agent must run the relevant checks and then run `xiaoqi_harness/deploy/deploy_current.ps1` before claiming the task is complete. Do not ask the user to run the deployment command.
- Do not deploy for Flutter-only UI changes, documentation-only changes, test-only changes, or comments/formatting that cannot affect the running service. When uncertain, inspect the actual diff and deploy only if the ECS runtime or its API behavior can change.
- If required checks fail, do not deploy broken code. Fix the failure first; if it cannot be fixed within the task, leave the current healthy server untouched and report the blocker. If deployment starts and fails, rely on the scripted automatic rollback and verify that the restored service is healthy.
- Every final report for a development task must say either “server deployed and verified” or “server deployment not needed”, with one plain-language reason. Local implementation, server deployment, and verified effectiveness must not be presented as the same milestone.
- When Alibaba Cloud authorization is needed, launch `aliyun configure --mode OAuth --profile xiaoqi-remote-deploy` so the user can authorize in the browser. Never ask the user to paste access keys or passwords into chat.
- Preserve the remote service's existing environment, secrets, and persistent data. Keep exactly one emergency restore point and report any deployment or verification blocker explicitly.
- Preferred deployment workflow: if authorization is needed, start the OAuth flow above and let the user complete login in the browser; never request credentials in chat. Then identify and confirm the target ECS and its running service with read-only Cloud Assistant commands. After reviewing and checking the authorized changes, commit the coherent release to `main` and push normally, without force-pushing or including unrelated work. Use `xiaoqi_harness/deploy/deploy_current.ps1` as the deployment entry point: it requires a clean local `main` matching `origin/main`, waits for the exact main commit's GitHub Actions artifact, then delivers the verified prebuilt artifact through Cloud Assistant (`SendFile`/`RunCommand`). Do not create a separate build branch or an uncommitted source snapshot. An expired artifact may be rebuilt from the same main commit by workflow_dispatch; another branch or commit's artifact must never be substituted. Recheck main before activation. Do not build Docker images or compile Dart on the production ECS, and do not fall back to an on-server build when CI fails. The build runner must use the same containerd image storage as production and verify an actual image export/import roundtrip before uploading the artifact. Keep server credentials and persistent data out of GitHub and the artifact.
- Before replacing files or restarting services, check disk, available memory, architecture and current health; create or refresh the single emergency restore point, record the running image/revision, and preserve environment files, secrets and persistent data. Load and verify prebuilt images on ECS, run the synthetic runtime gate, then hold ordinary requests while backing up, activating and checking data, public health, release and API contract. Resume traffic only after verification. Restore the recorded release automatically if activation or verification fails. Run the remote job independently of the Cloud Assistant connection; a polling failure must not trigger a duplicate deploy or delete active inputs. Keep complete deployment logs and retrieve them in bounded chunks. After success, keep only the current release and one non-running emergency restore point, and remove older project images, backups, staging uploads and temporary files. Report build, deployment, data and health verification separately in plain language.
