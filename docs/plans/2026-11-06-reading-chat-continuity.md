# Agent 通用上下文策略与机制修复方案

创建：2026-11-06 · 修订：2026-11-11 · 状态：已进入实现与发布验证

## 1. 目标与范围

本次修复覆盖服务端 Agent 从接收输入、恢复历史、理解意图、读取材料、调用工具，到等待用户、压缩、恢复和生成最终答复的整条上下文链路。成功标准是：每一阶段都能依据当前分支、当前目标和同一工作修订做决定；用户已经提供的信息不会因工作结束、阶段切换或补发材料而无故丢失。

连续追问、回答“是的”、补发附件是本次发现问题的入口和必过回归用例。规则必须同时适用于其他措辞、其他能力、其他附件类型、长对话、用户纠正、模型切换及中断恢复，不能按技能名、关键词或某张截图写特例。

落实既有[统一能力契约第 7 节](2026-11-04-unified-capability-contract.md#7-统一上下文构造与资源链路)：原始轨迹保留，推理视图可重建；目标、约束、待答事项和实际执行事实有可信来源；不同阶段按职责取用同一修订的信息。优先复用当前 Genkit、任务存储、附件服务、权限和恢复机制。

本次按服务端修复规划，沿用当前聊天、附件入口和等待状态，不安排前端交互设计、设计稿或页面改版。客户端请求和分支行为作为边界验证对象。发布标识同步属于既有发布流程；如果查出满足目标必须修改请求契约，先记录具体缺口和两端影响，再调整实施范围。

## 2. 已有证据与尚待验证的风险

2026-11-06 的只读生产调查已找到与截图、录屏对应的任务和附件，详见[诊断记录](../../.codex-artifacts/context-diagnosis-20261106/diagnosis.md)及其原始摘录。2026-11-11 续作时复核了相关本地源码；本轮没有重新检查生产健康。

| 层次 | 发现 | 结论边界 |
| --- | --- | --- |
| 历史与工作范围 | 澄清被记为完成；下一轮新建工作，客户端按工作筛选消息，服务端再次筛选并写回会话 | 已确认可以切断同一聊天的上下文。工作完成不能等同于聊天历史失效。 |
| 意图路由 | 只接收近期用户文字，缺少 AI 上一轮问题；澄清会直接结束本轮 | 已确认影响短答和补材料，主 Agent 没有机会补救。 |
| 附件 | 关联图片已就绪，但失败任务在实际读取之前返回；空的原始文本覆盖了默认概括意图 | 已确认这些案例不是上传失败。附件引用存在也不代表内容进入模型。 |
| 窗口与压缩 | 上述失败未进入主 Agent 压缩；五条短消息本地输入未发生压缩 | 没有证据证明这几次故障来自窗口耗尽；仍需检查长对话和各阶段预算。 |
| 旧技能与摘要 | 当前中间件先摘要，再过滤历史技能正文 | 源码可见的污染风险：旧说明可能已进入摘要。尚未声称复现了对应生产故障。 |
| 恢复与多入口 | 手工检查点缺少父快照关系；普通回合、后台任务、运行中补充输入等入口各有适配路径 | 必须纳入统一机制验证；不能仅修首次聊天调用。 |

## 3. 统一规则

### 3.1 四类信息各自保留可信来源

这四类信息是现有数据的职责划分，不新增四套存储，也不复制一份完整聊天数据库。

| 信息 | 权威来源及用途 | 不能发生的混用 |
| --- | --- | --- |
| 分支对话 | 选中快照及合法父链上的原始用户消息、公开答复；供理解指代、纠正和上下文 | 为当前工作裁剪的视图不能覆盖原始历史；不能混入兄弟分支。 |
| 工作状态 | 现有任务、范围契约和中断记录；保存当前目标、仍有效约束、待答事项、完成条件、能力版本及修订 | 工作结束不删除聊天；“是的”不能脱离对应问题独立解释。 |
| 材料与证据 | 原消息绑定的逻辑附件 ID、资源记录、读取结果和产物引用 | 文件名、上传成功、摘要和临时路径都不能替代实际内容证据。 |
| 权限与执行事实 | 现有授权、撤销记录、工具调用身份、结果回执及恢复状态 | 文字历史或摘要不能扩大权限；摘要遗漏不能让已经完成的操作再执行一次。 |

用户过去明确提出且仍适用的约束应继续有效；用户本轮的纠正和明确换题更新其适用范围。旧任务中的指令可以解释前文，但不能被自动当作新任务重新执行。仍有效且适用于当前动作的授权继续复用，不能因重建上下文而无故要求重复批准。

上传文档、截图、网页、文件名和工具输出按资料处理。其内部的“请执行”“忽略规则”等内容不得变成用户请求。当前已验证技能提供处理方法，不能自行改写目标或权限。

### 3.2 一个回合入口，一套状态，不同阶段按需取用

在现有运行时入口收敛上下文组装，形成可重建的内部回合视图。最小信息包括：

- 来源身份：租户、会话、选中快照、消息、任务和工作引用。
- 当前依据：工作修订、用户原始输入、有效意图及其来源、目标和仍有效约束。
- 连续状态：有效待答事项、相关双方对话、完成条件、已完成和结果未知的动作引用。
- 资源依据：当前能力版本、相关附件/产物、可读取状态及内容证据引用。
- 推理记录：本阶段预算、压缩修订、来源范围和未能恢复的片段。

上述信息优先从现有记录读取；只为缺失的待答、来源和修订信息补充内部元数据。字段命名和具体落盘位置随代码审查确定，不能把临时模型判断另存为一套独立事实。

| 阶段 | 必须能获得的信息 |
| --- | --- |
| 初始路由、运行中重新路由 | 最新输入、当前目标与约束、待答问题及其上文、相关双方对话、能力和材料概况 |
| 主 Agent、只读材料理解 | 路由所依据的同一修订，以及本步需要的技能、材料内容、执行记录和完成条件 |
| 子 Agent、插件命令 | 父任务明确委派的目标、必要证据及已核验权限子集；不自动获得整个父会话 |
| 最终回答与完成校验 | 当前完成条件、实际成果、读取覆盖范围、失败或未知结果、仍缺的输入 |
| 重试、恢复、MCP App 动作 | 原任务或来源绑定、有效中断/动作标识、当前修订、已提交结果；不能把 App 页面内容当成新的自然语言授权 |
| 摘要调用 | 已按来源和范围处理的推理资料、来源引用；不执行工具，也不直接变更工作或权限 |

无会话身份的独立后台任务按其已验证请求构造上下文，不从账号的“最近聊天”猜测历史。内部子任务和工具循环继承所属工作修订；需要新修订时重新核验，不各自猜测用户目标。

## 4. 具体修复机制

### 4.1 保存原始历史，独立构造推理视图

1. 保留现有工作范围校验。把当前工作允许使用的工具记录、能力和产物，与当前聊天可供理解的公开问答分开取用。不能直接删除现有过滤，否则会连带扩大产物和权限范围。
2. 正常路径从完整的当前会话状态读取。对已经被旧逻辑缩窄的快照，利用 SDK 的父快照和现有 CloudSessionStore，沿选中分支恢复缺少的公开问答。每个历史结算节点只抽取其对应回合，按稳定消息 ID 去重，不能拼接多份累积消息数组。
3. 核验租户、会话、工作流和父子关系。已结算任务结果只有能绑定到对应消息/快照时才可用。不得通过“最新叶子”替代用户明确选中的快照，也不得扫描兄弟分支凑历史。
4. 推理视图不写回为会话原文。保存当前轮的新消息、状态与原始回执，保持原有消息身份和来源；手工检查点补齐合法父关系。压缩只保存派生元数据，不破坏原始内容。
5. 祖先恢复使用有界、可取消的查询，检查循环与断链，优先利用已有完整快照。查询达到限额只标记“尚未取全”，不能据此宣称没有前文或永久丢弃历史。需要更早依据时沿可信引用继续读取。
6. 分支切换和删除后的后续请求以当前选中路径为准；不重新引入被移除的回复子树。只有本机存在、服务端未保存的历史，或已断裂且无可信来源的旧记录，不能凭模型补写。

### 4.2 统一本轮有效输入和指代

保留原始请求用于消息绑定、幂等校验和审计；另外生成一次有效意图，让路由、材料理解和执行共用，避免各阶段重新猜测或修改请求指纹。

处理顺序：

1. 用户本轮明确提出任务、修正、取消或换题时，以该输入更新当前目标；不强行塞回旧待答。
2. 输入是在回答有效问题或补充所需材料时，结合该问题和工作状态解释。“是的”“第二个”“按刚才的要求”等都按关系理解，不维护特殊词汇白名单。
3. 有附件但没有文字时，有明确待续目标就补齐该目标；没有待续目标则沿用现有只读概括意图。选择一个能力本身不等于要求执行它。
4. 无法确定对象或必要选择时，只问缺少的一项，同时保存已收到的资料。多选问题后的“是的”仍可能不足以选中一个方案。

路由必须看到相关 AI 问题和用户回答。材料概况足以判断任务时直接进入处理；需要材料内容才能判断时进入受限的只读理解，再决定是否澄清。该步骤复用附件服务，不增加一个能执行任意业务工具的独立 Agent。

### 4.3 等待用户是可恢复状态

在现有运行结果中显式表达完成、需要用户输入、真实工具中断、取消和失败，统一映射到已有任务状态与状态制品。覆盖路由澄清、缺少材料、附件对象不明确、能力引导后真正等待输入，以及主 Agent 的补充信息请求。

- 待答记录至少绑定来源问题、工作修订、缺项类别、关联材料及状态。复用既有结构化 ask_user 中断标识；普通路由澄清增加相应内部待答信息。不要从问号、客套话或最终答复中的某个关键词倒推状态。
- 主 Agent 需要用户补信息时通过已有 ask_user 机制表达；固定引导和运行时早返通过类型明确的结果表达。对用户展示的文字与最终提交的等待状态必须一致。
- 下一条输入只能消费仍有效、属于当前分支的待答事项。普通确认不能替代另一个工具审批、联网授权或不同对象的确认；原有结构化恢复协议继续有效。
- 任务已完成仍允许普通追问。等待事项被回答、取消、换题或更新目标后失效，不能在后来一句短答上重新激活。
- 旧记录中误记为完成的提问可依据可信前文恢复语义和材料关联；不能由此恢复过期授权或直接重放旧动作。
- 已提交的等待答复在无新输入的断线回查中回放；真实 interrupt 恢复仍走原中断协议。路由超时、格式错误、模型故障和执行预算耗尽分别保留原因，不能冒充缺少用户信息。

### 4.4 附件与内容证据贯穿回合

1. 用逻辑附件 ID 和原消息绑定识别新上传，用资源服务的可信元数据确认 MIME、类型、归属和就绪状态；不依赖客户端缺省字段或从文件名猜类型。相同内容的两次上传仍保留各自消息绑定。
2. 相关材料来自本轮输入、当前待答所绑定材料、或用户明确指向的同分支历史材料。继承引用时重新验证归属、有效期和使用权限，不批量读取全部历史附件。
3. 统一处理图片媒体、文档片段/页面及现有服务支持的其他输入。只有引用时允许先说明已收到附件；只有真实读取并传入对应模型或工具后，才记录为已提供内容证据。不能靠提示词要求模型“假定看到了”。
4. 分开记录 ready、读取成功/失败、进入哪个阶段的模型输入，以及文档实际覆盖范围。材料很多时分段取用并保留页码/片段引用，不能读了开头就宣称处理全文。
5. 附件过期、上传未完成、解析失败、模型不支持该输入分别处理。目标保留，具体指出需要重发或重试的资料；已有授权的能力可用时沿现有路径处理，不默默更换模型或新增服务。
6. 切换模型时重新检查媒体能力和预算；切换技能时更新能力版本及资源范围。两者都不应清空公开对话，也不能沿用已经失效的材料读取状态。

### 4.5 按完整请求预算使用官方压缩

继续直接使用锁定的 Genkit 官方 contextCompression：@genkit-ai/middleware 0.12.0，peer genkit 1.44.0。沿用现有 Node 适配器，不重写压缩算法，不恢复已被替换的字符裁剪或自写动作摘要引擎。现有配置见[适配器说明](../../xiaoqi_harness/genkit_server/context_compression/README.md)。

- 预算按具体模型、阶段和本次输出预留计算，同时计入系统说明、工具定义、消息、媒体及必要安全余量。服务端软预算与提供商硬上限分别记录；不能把模型总窗口直接当成全部可用的历史输入空间。
- 路由、主 Agent、子 Agent、最终答复及摘要请求都检查各自完整输入。估算值与提供商实际 usage 分开记录，媒体估算不能简单使用 data URI 字符数。
- 删除上一版“路由最近 6 轮、主模型最近 12 轮”的新限制。预算允许时保留适用历史；超出时由官方组件裁剪大结果、处理重复内容并摘要。上游保留近期消息的配置不是允许宿主永久删除其余历史。
- 当前目标、用户明确约束、待答、撤销和完成条件由程序从权威状态注入。已完成/结果未知的动作保留可核验的回执引用，并在再次提交相同效果前检查原调用身份。可靠性不能只依靠摘要正确记住所有事实。
- **先处理来源与当前范围，再摘要。** 过期技能正文和不属于本轮的执行指令不进入摘要输入；仍有用的公开事实保留来源。原始消息不变，推理投影和官方压缩元数据通过稳定消息/工具引用关联，不靠会变动的数组位置猜测。
- 摘要绑定来源范围、工作修订及适用能力范围。范围改变后不能盲目复用旧摘要，发现与原文冲突时回读来源。修正前产生且无法核验来源的摘要视为失效，按原始记录重新派生。
- 保持工具调用与返回配对，恢复官方元数据时也要验证引用关系。摘要失败或组件降级后再次检查预算和必要状态；仍无法满足就保留进度、分段处理或报告具体失败，不丢掉关键条件后继续执行。
- 若上游接口无法安全回映压缩元数据，使用单独的可失效派生记录保存该视图；不能以覆盖原始历史作为捷径。先用实际适配器验证，不维护上游压缩源码分叉。

### 4.6 并发、纠正、恢复与重复执行

复用已有 steering sequence、request identity、存储记录 revision、取消信号和执行锁，明确它们在回合视图中的对应关系。文中的“工作修订”表示用户目标与范围的有效版本，不把每次存储更新都误当作目标变更，也不增加一套独立的全局版本计数器。

- 运行中的补充输入、能力撤回或目标纠正形成新的工作修订。重新路由和下一步执行必须刷新相应视图；失效阶段的结果不能覆盖新目标。
- 会产生外部效果的操作在提交前检查最新工作修订和有效权限，保留现有原子领取/执行边界。已经发出的操作按回执核实，不能声称已撤回。
- 断线、停止后继续、进程重启和相同请求重试均从已提交状态恢复。回放回复与重新执行分开；结果未知的效果先按原调用身份核查，不仅凭模型文字决定重做。
- 待答文本、来源消息、任务状态和恢复点应形成一致的提交关系。复用现有事务/存储能力，避免客户端已看到问题、服务端却只保存 completed 的中间状态。
- 跨版本恢复重新验证运行结构、资源及授权；对话可读不代表旧中断或审批仍可直接执行。

## 5. 代码落点与实施顺序

| 现有落点 | 改动职责 |
| --- | --- |
| api.dart 的 _runRemoteAgent、_runTask | 入口身份与原始输入、历史/工作视图分离、结果和待答提交、回放；审查两个入口是否丢失同样信息 |
| store.dart 的 CloudSessionStore | 精确分支父链读取、检查点关系、旧快照恢复及查询边界 |

| history_context.dart、official_context_compression.dart、context_compression/compress.mjs | 来源过滤顺序、阶段预算、派生元数据的正确回映；保留官方压缩实现 |
| attachment_service.dart、artifact_context.dart | 材料绑定、可读性和证据记录；保持资源与产物权限边界 |
| 现有范围契约、授权及执行回执机制 | 复用修订和动作身份；检查上下文恢复不扩大权限、不重复提交 |
| Flutter 的消息构造、快照选择、等待状态消费与分支删除 | 验证现有请求足够表达需求；当前按不修改业务交互实施 |

实施按以下顺序推进，最后作为一个完整服务端修复发布：

1. **固定入口和不变量。** 使用现有请求/快照夹具复现三条故障，列出各模型调用的上下文来源；先明确原始轨迹与派生视图边界。
2. **收敛历史与工作状态。** 修复保存、分支恢复、统一有效意图和等待提交；使初次调用、补充输入及恢复共用同一规则。
3. **贯通材料。** 修正类型、空文字、只读理解、跨轮引用与证据状态；覆盖失败、过期和重试。
4. **接通压缩与并发边界。** 修正来源过滤顺序和预算，验证工具配对、摘要失效、用户纠正及动作幂等。避免只修短对话便结束本轮。
5. **完成回归与发布证据。** 先检查真实发往模型的请求，再验证结果和执行记录；通过现有发布流程上线，单独记录目标设备验收。

本轮按上述顺序开始实现，优先复用现有测试夹具和存储元数据，不引入新数据库、向量记忆服务、新工具集合或新的运行依赖。跨聊天长期记忆、全库检索、自动续期所有旧附件、重建不可恢复旧历史不在本版范围。

### 5.1 本轮已落地的机制

- 服务端将选中分支的公开用户/助手文字与工作执行范围分开构造；能力、工具、产物和权限仍按当前工作范围过滤。
- 路由接收有界的双方公开对话，保留助手提问作为短答、纠正和补充材料的语义依据，并移除固定 6/12 轮截断。
- 纯附件请求不再被空的 `current_turn_text` 覆盖；附件读取与主回答共用同一有效意图，使用说明后的补图沿当前待答和引用消息绑定材料。
- 路由澄清及结构化 `ask_user` 都映射为可恢复的 `waiting_for_user`，持久化问题文本/中断类型，断线回查会回放状态制品。
- 官方上下文压缩继续复用，过期技能正文在摘要前排除；手工检查点保存父快照关系。
- 客户端只调整消息/材料请求的数据流，不改变聊天交互界面；完整分支对话保留，材料仍按工作和待答来源收窄。

截至本修订，定向服务端回归（API、路由、工作范围、附件）及 Flutter 静态分析已通过；完整服务端套件仍受既有外部模型密钥、Docker 沙箱和耗时测试环境影响，不能据此宣称全套通过。生产部署和真实设备验证待本轮发布门禁完成后分别记录。

## 6. 验收标准

使用以下场景组织必要回归，不穷举所有组合；关键不变量通过现有夹具覆盖，真实模型与目标设备补充端到端证据。测试不能只检查“没有报错”“session ID 相同”或最终文本包含某句。

| 场景组 | 必过行为与证据 |
| --- | --- |
| 连续对话与分支 | 前轮完成后能展开第二点、纠正目标、引用指定旧答复；切换分支后依据所选分支，删除回复后不复活其子树；请求中有正确来源，持久化原文未缩窄 |
| 待答与短答 | 单项确认、选项回答、否定、取消、换题、隔轮补充；关联正确问题，缺项补齐就继续，多义时只问剩余问题；等待、失败、普通完成和工具审批不混用 |
| 材料闭环 | 使用说明后补图、文字加图、纯图片/文档、同名多文件、显式引用旧附件、替换附件、失效和解析失败；核对媒体/正文进入实际请求及读取覆盖范围 |
| 长对话与压缩 | 预算内、跨压缩阈值、超长工具结果、多个摘要周期、模型切换和摘要失败；保留纠正、待答和执行事实，旧技能指令不混入摘要，原文和调用配对完整 |
| 运行与恢复 | 初始路由、重新路由、主/子 Agent、最终答复及后台任务；断线回查、Stop 后继续、重复请求、进程恢复、旧快照断链；视图修订一致，副作用计数符合原请求 |
| 范围与来源 | 当前/旧技能、仍有效授权与撤销、跨租户资源、兄弟分支、资料内嵌指令、MCP App 动作；没有权限扩大或来源升级 |
| 性能与可观测性 | 短对话不无条件增加摘要或材料理解模型调用；正常路径不反复扫描祖先；长历史查询可取消，调用次数、首响应时间和上下文量与修复前基线可比较 |

附件验证采用仅出现在图片像素或文档正文里的内容标记，不能放进文件名或测试提示中。分别记录“服务确实把内容发送给模型”和“真实模型确实据此回答”；前者不能代替后者。切换不同技能、措辞及已支持模型核对通用性，避免固定答案测试掩盖路由问题。

观测信息使用现有事件/诊断渠道：任务、阶段、选中快照、工作修订、消息及资源引用、待答引用、输入计数、预算/实际用量、压缩或排除原因、恢复缺口和读取覆盖范围。普通日志不记录完整聊天、原始附件、密钥或内部推理；需要核查内容时按原有访问权限回读来源。

验收分开报告：代码完成、自动化检查、真实模型验证、服务端部署健康/数据验证、用户真机验证，以及原故障是否已验证消失。必要服务端用例优先加入已有 remote_agent_api、intent_router_recovery、turn_scope、attachment_agent_runtime、capability_scope 等测试；运行与改动对应的现有门禁，不另造测试框架。

## 7. 旧数据、发布和回滚

- 不批量重写历史消息或补造丢失对话。新增内部状态允许读取旧记录的缺省值；这是持久化数据恢复，不是保留多套旧客户端请求格式。
- 有可信父链的旧对话按需恢复；没有可靠来源时保留已验证片段并说明缺口。新机制保证后续记录完整，不能承诺修复所有已经丢失的历史。
- 复用当前 API 字段和等待状态，目标维持契约 32，但需以实际请求/响应和恢复语义验证为准；一旦必须改变对外契约，按单版本规则同步更新两端，不能静默增加旧版本兼容路径。
- 正式发布仍须同步共享产品 release ID 并提供匹配客户端。现有校验同时比较契约和产品发布标识；即使业务代码只改后端，也不能承诺旧安装包继续通过版本检查。
- 按[已验证发布流程](../architecture/release-flow-validation-2026-11-05.md)完成当前准确 main 的相应检查和预构建产物，再运行 deploy_current.ps1。检查契约、健康、数据及受影响业务探针，失败使用脚本自动恢复。
- 回滚验证包括原始消息、任务、待答元数据、能力版本引用和未完成工作，不通过清空用户数据恢复服务。保留当前发布和一个非运行的紧急恢复点，保护被工作引用的能力历史。
- 自动化和线上探针通过之后，按手机现有入口验收连续对话、短确认和补附件。未完成真机验证前不得称为原故障已在手机解决。

本轮代码已修改服务端运行时、API 状态回放、Flutter 请求数据流和共享发布标识；因此需要按既有发布流程完成服务端部署、健康/数据核对，再单独进行手机连续对话、短确认和补附件验证。部署或真机验证未完成前，不称为线上故障已消失。
