每个功能记录：入口 → App 预处理 → 请求接口 → 实际运行时 → 工具 → 存储 → App 展示。明确哪些请求经过 Harness、哪些仍直接请求模型、哪些是有意保留的业务处理。

## 2. 建立可追溯的基线，复现两次实际问题

负责人：AI。预计 2–4 小时；真实 PDF 获取及设备可用性另计。

1. 固定 App 构建、后端部署、Harness 版本、模型配置和个人账号开关，给每次测试记录任务 ID、尝试次数和时间。
2. 使用两段录屏对应任务的可用记录，追踪请求在哪一步失败或丢失。无法定位时标记“证据缺失”，采用受控样例重新复现。
3. PDF 检查提取结果、分段请求、模型响应字段、结束原因和错误映射；CSV 检查工具调用、文件存在性、登记、存储、下载及 App 展示；草稿检查保存和重新读取。
4. 对照原有路径与 Harness 路径的输入、输出和状态。比较结果是否满足任务要求，不要求自然语言逐字相同。
5. 把问题按共同原因归类：输入丢失、协议不匹配、工具缺失、状态不一致、产物丢失等，再确定修复位置。

产物：问题表，包含“复现步骤、预期、实际、证据、根因或待验证假设、影响功能、修复位置”。日志仅保留诊断所需信息，不记录密钥或整份私人资料。

通过标准：两次实际问题均有证据支持的原因，或明确列出还缺什么。拿不到 book.pdf 原文件时，可先检查同类 PDF，但必须保留原文件复测待办，不能宣称该文件已修好。

## 4. 按功能矩阵验收，包括真实停止与恢复

负责人：AI。预计 3–6 小时；设备连接和故障修复时间另计。

以下是最低覆盖范围。阶段 1 发现其他既有支持格式、工具或入口时，加入同一矩阵；未支持的新功能不自动纳入开发范围。

| 功能 | 必测样例与动作 | 通过证据 |
| --- | --- | --- |
| 资料读取 | 短文字、长文字、文字 PDF、扫描 PDF；原 book.pdf；空文件或损坏文件 | 已知事实可定位到原资料；长资料首尾内容未丢；无法读取时明确报错 |
| 技能读取 | 技能正文与资源分别设置可核对内容，再实际调用技能 | 工具记录和结果证明正文、资源都已读取；缺资源如实失败 |
| 草稿与保存 | 新建、修改、读回、保存、重新打开并调用；保存失败 | 草稿修改一致；正式保存后重进仍存在；失败不假装已保存 |
| Python 与文件 | 两组不同数字生成 CSV；另一个既有支持的文件类型；工具报错与存储失败 | 真实工具记录、正确文件内容、实际下载并打开；写出本地路径不等于交付 |
| 联网授权 | 未授权、同意、拒绝；恢复后再次请求超出授权范围的访问 | 未授权访问被阻止；同意后继续同一任务；拒绝可理解且不绕过权限 |
| 取消 | 在模型等待、Python 执行、等待授权、文件提交阶段分别取消 | 取消请求、执行终止、沙箱释放均可关联；观察期内无继续计算或迟到结果覆盖状态 |
| 超时与终止失败 | 触发任务超时；模拟停止调用失败 | 有明确终止原因；清理失败不能显示已彻底停止，并有可执行清理措施 |
| App 恢复 | 离开页面、关闭重开、短时断网后重连 | 恢复同一任务及真实状态；不重复提交；已完成文件仍可下载 |
| 服务恢复 | 中断 worker 或恢复过程 | 状态可解释；未知结果的副作用不盲目重放；不可继续时如实失败 |
| 历史与重复操作 | 打开旧会话、旧任务和旧文件；重复点击提交或保存 | 旧数据可用；没有重复任务、重复保存或重复执行 |
| 账号边界 | 在受控测试身份下尝试跨身份读取、下载、取消 | 服务端拒绝越权；个人账号之外的新任务不误入试跑路径 |

取消验收必须记录：点击时间、服务端收到时间、运行时停止时间、沙箱终止确认时间。先核对现有超时与重试配置，再冻结允许停止时限和观察窗口；观察窗口覆盖可能的迟到回调及重试。未确定标准或未完成观察，不标为通过。

授权后续跑、App 重开恢复、服务中断恢复是三个独立用例，不能互相替代。运行完成与取消同时发生时，核对已确定的终态和结果归属，不让迟到事件改写状态。

移动端先按项目规范用 ARTEMIS 探索真实页面，再编写需要的移动测试。若工具或设备不可用，先诊断；后端验证可继续，但 App 项目保持“未执行”，不以后台测试替代。

产物：每行有用例编号、版本、输入、预期、实际、证据位置和状态的验收表。状态只使用“通过 / 失败 / 未执行”。新改动只重跑受影响项与关键回归；没有新风险时不反复全量测试。

## 5. 个人账号体验与最终判定

负责人：用户体验，AI 准备步骤并核对后台证据。预计用户操作 10–15 分钟，模型等待时间另计。

进入条件：前四阶段必验项通过。若 App 自动验证因设备条件未执行，先明确列出这些待验项，用户操作仅用于补齐验收，不提前宣布前四阶段通过。

届时提供最多五项的操作清单：

1. 读取指定资料，核对三点摘要及其依据。
2. 修改并保存技能，重新打开后调用。
3. 生成文件，点击下载并打开检查内容。
4. 同意及拒绝联网请求，观察对应结果。
5. 执行较长任务并取消，再做一次关闭重开恢复；AI 同时核对后台终止与任务 ID。

用户只需逐项回复“通过”或指出失败位置。出现问题后由 AI 收集证据、修复并重测相关项，避免让用户反复提交相同任务。

最终记录分别注明：代码完成、自动化与静态检查、目标平台验证、部署版本、实际体验结果。必要项有任何“失败”或“未执行”，结论仍为“完整接入待验收”。全部通过后，结论限定为“本方案覆盖的原有功能在个人账号范围验收通过”；扩大账号范围需要另行决定。

发现越权、取消失效、重复执行或虚假成功时，停止继续扩展试跑。必要时回退个人账号后续新任务的路由；在途任务按原运行时终止或完成，不双跑、不自动重放。

阶段 1 发现的关键缺口：视频二测到的是普通聊天的旧附件摘要路径；视频一的文件正文自称已生成，App 端文件卡片和系统保存路径现已接入但未经端到端验证；技能仍需完整验收草稿读取、回传和保存。Harness 后端单项通过不能替代 App 端验收。个人账号租户限制以前已核实，本轮未改云端配置；继续前仍需按部署记录复核。

阶段 2 初步诊断：PDF 错误的**直接原因**已定位为空摘要响应；**根因**无法从视频或服务器 Harness 日志确认，因为普通聊天摘要请求由 App 直接调用模型，没有对应 Harness task ID，当前错误也没显示模型请求 ID/结束原因。精确修复前需补充不含附件正文和密钥的响应诊断，再用相同路径复现。普通附件聊天是否属于本次要迁入 Harness 的范围，依据已确认的任务范围执行；若范围文档没有明说，先保留现有直聊行为，单独修复并验收它，不以扩大路由掩盖空响应。

阶段 1 补充核查（2026-10-05，修复前基线）：

- 当前锁定的 E2B 依赖为 `e2b==2.31.0`、`e2b-code-interpreter==2.8.1`；Harness/ACP 依赖分别为 `deepseek-harness-sdk==0.1.5rc1`、`agent-client-protocol==1.0.0rc2`。
- `cancelTask()` 只发 POST 并检查 HTTP 状态；`home_page.dart` 用 `unawaited(...catchError)` 调用它，随后立即结束本地生成状态，因此 App 没有显示服务端停止确认。
- API 在停止沙箱失败时会写入 `sandbox_cleanup_pending` 与 5 分钟 deadline；全仓搜索只有写入位置，没有读取/重试清理任务的代码。失败路径的最终释放没有仓库内的主动保障。API 仍返回 200 和 `cancelling`，没有把清理失败传给 App。
- App 的 `watchTask()` 只把 `succeeded`、`failed`、`cancelled` 当作终态；若一直停在 `cancelling`，20 分钟后以超时报错结束监听。
- 阶段 2 查到 E2B 官方 Python SDK 说明：`Sandbox.kill(sandbox_id)` 成功返回 `True`，找不到该沙箱返回 `False`。需结合任务记录和 E2B 沙箱列表验证实际清理；API 目前只返回任务状态，不返回清理确认字段。
- 2026-10-05 更新首页任务入口：已登录的个人账号发送首页消息后统一创建 Agent 任务，不再要求先选择能力或保存技能；邮箱账号同步会话沿用为 API 授权凭证，不需要设备配对。已选能力仍作为可选能力上下文，附件仍走现有准备流程。API 侧仍按租户、模型和图片兼容性选择 Harness 或旧运行时，需在后续版本核对与验收。
- 现有后端测试包含排队任务取消、模型返回迟到结果丢弃、正常 Python 沙箱清理；没有覆盖沙箱停止端点失败后的清理重试，也没有覆盖 Flutter 点击停止后等到云端终态的完整路径。
- Harness 取消路径已实现协作停止：运行中的 ACP 提示每 0.75 秒检查取消标志；发现取消后调用 `connection.cancel(session_id)`，并在超时后取消本地 prompt 协程。Harness worker 随后把任务写为 `cancelled`。当前测试没有覆盖这条 ACP 取消路径。
