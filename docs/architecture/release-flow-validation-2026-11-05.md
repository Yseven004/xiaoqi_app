## 固定的执行规则

1. 以最近通过累计检查规则的成功 main 为检查基线；失败补丁不能遗漏此前未验证改动。旧规则不能充当新规则的已验证基线。
2. 按实际组件指纹复用镜像；保留真实构建来源，当前发布清单对应准确 main；无匹配成品则只补建缺失组件。
3. 业务检查按范围执行，能力包测试在独立仓库执行；每次实际生产切换仍保留候选探针、备份、版本/健康/数据检查及可靠回滚。
4. 失败先检查原任务阶段和日志；连接中断只跟踪原任务，写操作不盲目重试。
5. 成功后保留当前发布与一个非运行恢复点；手工代码回滚保留当前用户数据。以上流程已通过本次自动化、隔离环境、生产和复用样本验证，作为后续默认流程。

## 2026-11-11 检查范围与镜像复用修订

本次上下文修复的首次发布暴露出检查选择过宽：服务端任意 `lib/**` 改动都会进入串行完整 Dart 套件，且默认运行全量能力探针。发布流程现改为：

- `agent_runtime.dart`、`api.dart`、`intent_router.dart`、附件/上下文相关实现只运行对应的 Agent、路由、范围、附件回归；未命中明确影响范围时继续运行完整服务端套件。
- 图片服务、图片能力链探针或其直接测试变更才选择 `full` 运行探针；其他服务端行为使用 `non-image` 探针，但仍保留 API 契约、健康、数据、恢复点和受影响业务检查。
- `Dockerfile` 测试阶段接收受控的 `DART_TEST_ARGS`，路径选择器只产生仓库内固定测试文件和并发参数，不能由提交内容注入任意命令。
- 发布包仍包含四个固定组件：Genkit API/Agent、sandbox runner、代码沙箱和 sandbox proxy。组件指纹与基础镜像身份匹配时，从最近成功产物复用未变镜像；完整组件集合是为了生产加载、身份核对和回滚，不代表每次都重建四个镜像。
- 手动或基线恢复仍可选择完整套件；缩小检查范围不会降低每次实际激活的备份、健康、数据和自动回滚门禁。

本修订本身只改变 CI 检查选择与测试参数，不改变运行时 API；需通过一次新的发布流程验证其耗时与复用证据。
