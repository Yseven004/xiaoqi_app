## 结论

确实存在限制粒度过粗的问题。主要来自项目自己叠加的工具过滤和审批逻辑，并不是 Genkit Dart 1.0 强制所有工具都必须逐次确认。

最先值得调整的三处是：MCP 全工具逐次审批；显式选择技能后隐藏通用代码工具；让一次前置意图分类结果直接裁掉后续技能发现能力。这三处叠加后，会出现“已安装、已连接，但 Agent 无法完成调用链”的情况。

此外还有工具目录硬上限、精确域名出网、导入/安装拦截和运行宿主缺失等问题，全部纳入本方案。最终按真实技能/插件的完整任务闭环验收。目前没有用户提供的具体失败会话或生产 trace，本报告不把静态可触发的路径冒充某次线上故障的已证实原因。

## 已核对的调用链

| 阶段 | 当前实现 | 对正常任务的影响 |
| --- | --- | --- |
| 导入与依赖准备 | 按工具名称、脚本后缀、构建文件和组件类型静态判为不支持；安装器限制依赖来源和构建过程 | 部分能力在进入 Agent 之前已经被整体排除 |
| 账号与安装版本 | 从当前账号加载启用的技能、插件和 MCP 连接；绑定不可变版本 | 这是账号和版本边界，应保留 |
| 前置意图分类 | 生成 `TurnContract`，确定工作模式、技能 ID、连接 ID和生图预算 | 分类错误会变成后续硬权限错误 |
| 裁剪目录 | 删除未被分类器选中的技能和连接，再计算工具可用性 | Agent 可能失去发现和修正分类遗漏的机会 |
| 构造工具集合 | 根据工作模式和是否显式选技能过滤工具 | 技能和通用代码能力被做成互斥关系 |
| MCP 包装 | 每个远程工具都先 interrupt，批准时校验参数与本轮身份的摘要 | 读取、搜索和写入一律逐次确认 |
| 脚本联网 | 技能脚本只要声明域名，就构造一次新的联网确认 | 即使搜索开关开启，也不会直接执行 |
| 执行与交付 | 在隔离容器执行脚本，或调用当前账号的 MCP；记录真实产物与交付证据 | 应保留真实执行证据，同时去掉不必要的前置次数约束 |

## 具体发现

### 1. MCP 不区分操作性质，全部逐次审批：高优先级

位置：`agent_runtime.dart:2223–2257`。

所有 MCP 工具的描述都写着“等待用户确认后才执行”。执行函数无条件要求 `resumed.approved == true`，并匹配 `approval_hash`。这一分支没有使用 MCP 工具的 `annotations`，也没有区分查询、创建草稿、发送或删除。

另有一层独立门槛：`agent_runtime.dart:2231` 调用 `execution.check('workflow')`，而 `tool_execution.dart:69` 会拒绝非工作流模式。即使 MCP 只用于回答问题时的资料查询，也可能因为前置分类是 `answer` 而失败。

现有集成测试 `capability_runtime_test.dart:255–262` 明确断言批准前远程调用为 0；成功和错误场景本轮均通过。这证明现有审批路径能够运行，不证明这种产品规则适合所有工具。

建议：查询和任务工作区操作默认执行；外部操作按用户对具体动作、对象和范围的授权决定是否需要确认。已明确授权的操作直接执行，授权改变时重新判断。审批判断与工作流模式分开。

### 2. 显式选中技能后，通用代码工具被隐藏：高优先级

位置：`agent_runtime.dart:1655`、`3112`、`3124`。

`skillSelected` 来自显式技能集合是否非空。构造工具目录时使用 `codeExecutionAvailable: codeExecutor.isConfigured && !skillSelected`。技能若没有 `scripts/` 下受支持的脚本，`execute_skill_script` 也会被移除。

因此，一个只提供流程说明的技能，可能同时没有通用代码执行和技能脚本执行。即使技能需要简单的数据转换、文档生成或运行一段辅助代码，也无法通过现有工具完成。

建议：技能执行与通用执行可以同时可用。技能文件使用绑定版本，临时辅助代码在同一任务的隔离边界内执行；不要用隐藏整个执行工具来实现版本或联网控制。

### 3. 意图分类同时承担了能力授权：高优先级

位置：`agent_runtime.dart:1587–1623`、`767–794`；`turn_contract.dart:124–129`。

分类后，`selectedSkills.entries.removeWhere(...)` 和 `explicitIds.retainAll(...)` 会删除未入选技能。非工作流模式的 `skillIds` 又被清空。工具目录的 `use_skill`、`read_skill_resource` 也依赖工作流模式及非空技能集合。

这会形成静态可触发的封闭路径：分类遗漏技能 → 技能从目录删除 → Agent 无法再读取技能 → 后续推理无法纠正遗漏。分类器异常时，`agent_runtime.dart:981–988` 还会返回带澄清信息的 `answer` 契约，后续直接回复澄清并结束准备阶段。

建议：分类器只推荐能力和约束用户明确禁止的效果；当前账号已启用能力仍可发现。执行前再判断具体动作是否属于用户任务。保留取消、最新用户指令、目标产物和生图数量约束，不让分类器一次漏判变成永久不可调用。

### 4. 技能联网与通用代码联网规则不一致：高优先级

位置：`agent_runtime.dart:2945–2984`、`3953–3969`。

当前远程 Agent 的普通代码联网会按任务登记申请域名，不再逐域名询问；技能脚本却对每次非空域名列表重新构造 `NetworkPermissionRequired`。连接是否需要确认，被“是否为技能脚本”这一粗分类决定，而不是实际外部动作。

已有确认规格也必须遵守：`docs/design/skills-plugins-v1-state-spec.md:80–88` 规定 `off` 表示普通对话不联网，但有效技能可为本次调用临时联网；临时域名不写入持久允许列表。当前技能脚本批准分支无条件调用 `_authorizeAgentTaskDomains`，与“临时授权不持久化”存在静态实现偏差。

建议：沿用现有搜索开关语义，统一普通执行和技能执行的出网判定；将“能连接公网”和“能执行某项外部操作”分开。搜索/读取所需连接不反复打断；发送、删除或付费的授权应绑定实际动作。临时联网只传给本次执行，不写成后续可复用的任务授权。

### 5. 目录大小限制会拒绝整个连接器：中优先级

位置：`mcp_connection_service.dart:16–34`、`agent_runtime.dart:2204–2209`。

远程发现支持分页，但累计超过 100 个工具就抛错；注册时所有连接器工具合计超过 64 个，又会抛错或跳过整个连接器。两层上限并不一致。一个提供 65 个工具的显式连接器，即使当前只需其中一个工具，也无法进入正常注册路径。

建议：区分“完整目录可检索”和“本次发给模型的工具集合”。按需发现与加载，工具多不等于整个连接器不可用。数量控制保留为上下文和资源预算，不作为整连接器拒绝条件。

### 6. 多步产物复用只覆盖部分文本类型：中优先级

位置：`code_execution_service.dart:353–428`；`sandbox_runner/server.py:374–447`。

每次调用确实创建新的工作区，但已有产物回注机制：最近的部分文本产物会作为下一次执行的材料重新提供。不能描述为“多步调用完全无法复用文件”。现有文本复用测试本轮通过。

限制在于回注扩展名、媒体类型和数量：例如 XLSX、DOCX、PDF、PNG 等二进制产物不在当前回注集合内。这会影响“生成 → 再处理 → 导出”的技能链；它属于工作区能力问题，取消审批本身不能解决。

建议：先实现同任务产物按 ID 显式读取或挂载，覆盖二进制内容，继续校验账号和任务归属。优先复用现有存储和执行入口，不先改成长驻容器。

### 7. 本地命令型 MCP 和部分脚本类型尚无宿主：能力缺口

位置：`plugin_dependencies.dart:80–89`；`code_execution_service.dart:140`；`agent_runtime.dart:1656–1663`。

插件声明中含 `command` 或没有远程 URL 的 MCP 会被标记为“需要尚未支持的本地宿主”。技能脚本入口只接受 Python、JavaScript、TypeScript 及其列出的扩展名。

这不是一个审批开关。要支持 stdio MCP、Shell 入口、浏览器或设备能力，需要相应宿主和工具接入；不能把“不支持”改成“允许”后宣称已兼容。现有 Python/Node 代码本身可以在沙箱内调用可用程序，不能笼统地说“完全不能执行命令”。

建议：把 stdio MCP、Shell 入口、浏览器/设备宿主及平台适配全部纳入总问题台账，分阶段交付。每类都要有真实运行样本和取消/恢复证据，缺少宿主的项目保持未完成，不能只修改错误提示后关闭。

### 8. 预算与交付检查存在额外阻塞及一个独立计数缺陷

位置：`agent_runtime.dart:2266–2280`、`3488–3492`；`tool_execution.dart:95`；`code_execution_service.dart:331–344`。

- MCP 必须先在交付计划中声明精确工具及次数；成功次数达到计划数后，即使 Agent 发现需要补读一页也会被阻止。确认操作发生在该次数检查之前，可能出现用户已经确认、执行却仍被计划门槛挡住。
- 工作流操作预算为 24；准备阶段模型轮数依场景为 8/12/32。它们是独立限制，需要用代表性技能链测量后确定预算，不能统一宣称“已取消所有限制”。
- 技能脚本检查字段 `skill_script_runs >= 12`，但写回的是固定值 `1`，没有递增。现有测试只执行一次后手动写入 12，未覆盖真实累计 12 次。因此不能把当前“12 次上限”当作可靠生效的限制。

建议：低风险读取允许按实际需要调整次数；真实产物核验继续保留。为有效的费用、时间、资源预算做正确计数；不要用输出计划中的次数替代授权或资源控制。计数缺陷单独记录，不在本轮静默修改。

### 9. 导入、安装与组件检查提前整包拒绝：补充发现

位置：`capability_import_service.dart:630–667`、`773–795`、`822–846`；`bin/prepare_dependencies.py:15–43`。

- 技能 `allowed-tools` 中出现 `Bash`、`Shell`、`Computer`、`Browser` 或 `mcp` 字样就产生问题项，进而可能把整个技能标为 `unsupported`；其中 `mcp` 与现有远程 MCP 能力之间也未做具体依赖解析。
- `scripts/` 内出现允许后缀集合之外的文件，或包内存在 `setup.py`、`Dockerfile`，也会产生不支持项。静态检查没有充分区分可执行入口、辅助资源和实际构建需求。
- 只有 `pyproject.toml` 的 Python 依赖不会自动准备；当前 Python 安装仅接受二进制包，npm 安装/构建生命周期脚本被拒绝。原生依赖、需要构建或需要其他源的合法包可能无法安装。
- 插件 `hooks`、`commands`、`agents`、`apps` 以及客户端专有 `extensions` 均存在尚未执行或不支持的判断。

建议：导入时生成真实的组件与运行需求清单，再匹配可用宿主、适配器、依赖和账号授权。为已纳入目标的缺失能力补实现；对独立组件保留独立状态，避免一个辅助资源或未就绪组件拖垮整个包。依赖安装/构建在无平台秘密的隔离环境中完成，产出锁定版本和校验信息；不在生产 ECS 上构建服务镜像或给用户 Dockerfile 直接提供宿主 Docker 控制权。

这些新增条目是源码核对得到的能力缺口或静态阻断路径，本轮未执行其安装与运行复现。

## 推荐的目标规则（尚待用户确认）

目标是让用户已启用的技能/插件完成任务闭环，减少无必要的中断，同时保留账号、凭据和任务隔离。

| 动作 | 建议默认行为 | 判定依据 |
| --- | --- | --- |
| 发现工具、读取技能说明及引用资料 | 直接执行 | 当前账号已启用、当前版本有效 |
| 搜索、读取远程资料 | 任务内直接执行 | 当前任务需要、连接已绑定；遵守已确认的联网搜索规则 |
| 隔离工作区内转换文件、执行辅助代码、生成产物 | 直接执行 | 任务归属有效、资源预算可用 |
| 用户明确要求的对外发送、修改、删除或付费 | 在授权动作和范围内直接执行 | 用户指令或用户确认；校验对象、参数、数量与额度 |
| 任务未明确涵盖的外部高风险动作 | 使用现有确认交互，说明具体对象和影响 | 得到这项动作的明确授权后执行 |
| 跨账号取数据、把平台密钥交给技能、访问宿主控制面 | 拒绝 | 与任务执行能力分开保留的基础边界 |
| 缺少宿主、依赖或连接 | 明确报告缺失能力及可行恢复入口 | 真实运行能力，不能用权限放开替代 |

MCP 的 `readOnlyHint`、`destructiveHint` 等只能作为操作分类线索，不能因为远端自称只读就直接获得额外权限。优先使用服务端维护的可信连接器规则、用户授权与实际参数；未知工具不因名字包含 `read` 就自动视为只读。

基础权限交互优先沿用现有界面：普通读取不弹卡片；确需确认的外部操作使用现有审批卡片，保留拒绝、取消、恢复和参数变更后的重新判断。宿主连接、设备选择、依赖准备和恢复等新增交互，实施前按项目 Product Design 流程确认。本次没有冻结新的 UI 规则。

## 全量问题台账与完成标准

所有条目当前均为“已纳入方案，未实施”。P01–P12 对应已发现问题或明确的运行能力缺口；P13–P14 是贯穿全部改动的闭环验收要求，不表示已经证实额外生产故障。

| 编号 | 必须完成的工作 | 关闭该项所需的结果 |
| --- | --- | --- |
| P01 | MCP 按具体动作授权，解除问答模式对只读 MCP 的阻断 | 查询无需逐次确认；明确授权的外部动作执行；范围改变、拒绝和撤销生效 |
| P02 | 技能与通用代码能力并存 | 无自带脚本技能可完成辅助计算、转换和交付；已安装脚本仍绑定正确版本 |
| P03 | 意图推荐与能力发现/授权分离 | 分类遗漏可由 Agent 发现并纠正；异常时仍保留合适的读取和恢复路径 |
| P04 | 统一联网与临时授权生命周期 | 搜索开关语义保持；技能按需临时出网；授权不跨调用泄漏，取消可撤销运行代理 |
| P05 | 大型 MCP 目录分页、检索及按需加载 | 超过原 64/100 工具门槛的连接器可完成目标调用，目录变化和分页异常有恢复路径 |
| P06 | 文本和二进制产物在同任务内复用 | XLSX、DOCX、PDF、图片及文本可连续读取、修改、导出；任务归属、路径和版本正确 |
| P07 | stdio MCP 隔离运行宿主 | 从插件声明到安装、启动、发现、调用、结束全部跑通；取消、超时、重启和进程清理可验证 |
| P08 | Shell 与通用命令入口适配 | 真实 Shell 技能可在隔离宿主运行；参数、工作目录、环境和子进程生命周期正确 |
| P09 | 浏览器、Computer 和设备能力接入 | 对已登记目标插件提供所需的真实宿主/桥接；权限、登录、目标选择、断连和取消有闭环 |
| P10 | 导入与依赖/构建兼容 | `allowed-tools`、辅助资源、pyproject、安装脚本和自定义构建需求按实际能力处理；代表样本可安装并执行 |
| P11 | 插件组件与宿主专有扩展适配 | hooks、commands、agents、apps、extensions 按目标插件协议实现或映射；必要组件不再只提示“不支持” |
| P12 | 预算、计划次数及计数缺陷 | 补读不会被计划次数误拦；资源预算正确累计，并发/失败/恢复后不重置、不重复扣算 |
| P13 | 失败、取消、恢复、幂等与调用证据 | 所有入口共用可追踪生命周期；安全读取可恢复，结果未知的副作用不盲重放，残留资源可清理 |
| P14 | 客户端交互、协议、部署和真实效果 | 对应交互验收、版本匹配、自动化、目标平台、服务器部署及代表任务效果全部有分项证据 |

不能用“代码已改”“静态检查通过”“已部署”中的任意一项单独关闭上述条目。每项至少绑定问题描述、目标样本、实施提交、自动化结果、适用的平台/服务验证和遗留阻塞；阶段完成不等于总任务完成。

### 目标样本与适配边界

实施阶段首先从实际启用、已导入及用户计划使用的技能/插件中固定验收样本，并为以上每类阻断补充最小可运行样本。清单记录来源、版本/提交、许可证、组件、工具与协议、依赖、运行平台、账号/数据要求、预期产物和验收证据。

本方案覆盖全部已登记问题；不以“兼容任意未来插件”作为不可验证的承诺。发现与本次问题有关的其他阻断时加入同一台账、说明范围影响，不静默排除。某个目标插件若必须依赖尚未取得的专有协议、特定硬件或用户账号，记录具体阻塞与解除条件，该项和总任务继续保持未完成；不能改为“不支持”后销项。

## 依赖与实施顺序

### 阶段 0：固定闭环、交互和验收基线

建立 P01–P14 台账与代表样本清单，补充可复现条件和现有调用证据。确认普通执行、外部动作授权、联网、宿主连接、安装、设备选择、失败恢复等用户流程；复用现有页面、卡片、事件和设计令牌，按 Product Design 流程完成必要交互共创。确定各平台的实际运行位置，不能默认云服务器能访问用户电脑或手机。

出口：所有已知问题都有预期行为、目标平台、验收样本和明确待定项；产品文档、设计和方案一致。当前文件是总体计划，尚未完成此阶段的实际样本与交互确认。

### 阶段 1：统一权限、用户授权和运行状态（P01、P04、P12、P13 的基础）

用小型共享决策入口统一 MCP、技能脚本和通用执行的 `allow / confirm / deny / unavailable` 判断，复用 Genkit interrupt/resume。区分账号能力、任务范围、实际外部动作、用户已有授权和当前可用宿主；授权绑定动作、目标和必要参数，用户更新/取消时立即失效。统一错误分类、操作身份、费用与资源计数，校正固定写回 `1` 的缺陷。

保留账号隔离、凭据代用、安装版本绑定、沙箱和真实交付核验。先补取消、幂等和授权变化的检查，再开放各执行入口，避免不同入口规则再次分叉。

出口：同一动作通过不同入口得到相同权限结果；查询不中断，已授权动作不重复询问，撤销/参数变化生效；预算及操作记录在失败、并发和恢复后仍正确。

### 阶段 2：打通发现、导入判定和工具组合（P02、P03、P05、P10 的导入部分）

去掉显式技能与通用执行互斥；分类器提供能力推荐，已启用技能仍可发现。将导入阶段的工具名称/文件存在性拒绝改为组件与运行需求解析，按组件记录缺失项；辅助资源不当作执行入口。大型 MCP 工具目录完整分页保存/检索，按需向模型暴露工具，处理稳定 ID、重名、目录变动及旧映射失效。

出口：无脚本技能、分类遗漏技能、含辅助资源的技能和大型 MCP 连接器均能进入正确执行链，不能以原 64/100 工具门槛整组拒绝。

### 阶段 3：统一联网、文件与多步任务工作区（P04、P06）

保持已确认联网搜索两态语义，临时联网授权只传给当次执行；统一代码、技能、依赖准备与 MCP 的网络目标检查和撤销路径。对合法重定向、子域名、包仓库及不同宿主所需协议逐项建样本，调整误伤正常服务的限制，并保留私网/元数据控制面的隔离。

复用现有对象存储，提供同账号同任务产物按 ID 读取/挂载；支持二进制和文本、多步修改、重名与版本关系。采用可验证的输入/输出记录，在临时执行环境重建必要状态，避免要求每步只能读取少数文本后缀。

出口：关闭搜索时技能可临时联网且不泄漏授权；连续文件生成、编辑和导出跑通；取消、重试或恢复后材料和产物归属不变。

### 阶段 4：补齐依赖、Shell 和 stdio MCP 宿主（P07、P08、P10 的安装/构建部分）

在任务隔离边界内运行命令和 stdio MCP 子进程。使用结构化命令、参数、工作目录和最小环境传递；分别处理 MCP 标准输出协议、诊断输出、启动就绪、调用超时、取消、进程树回收及重连。优先使用已锁定 SDK 支持的 MCP 客户端接口，不在 API 业务进程里直接运行任意插件宿主。

为 pyproject、需要构建的 Python 包、npm 安装生命周期及目标插件的自定义环境补准备流程，生成版本锁定与校验结果；安装脚本在隔离环境运行。自定义镜像如确有必要，交由独立构建环境产出并验证，禁止在生产 ECS 构建服务镜像、挂载宿主 Docker socket 或继承平台秘密。

出口：真实命令型 MCP、Shell 技能、需要安装/构建的目标包均可从导入走到交付；宿主升级、启动失败、取消和异常退出后无残留进程或跨任务状态。

### 阶段 5：补齐浏览器、设备与插件组件适配（P09、P11）

按阶段 0 确认的平台目标，提供浏览器/Computer/设备宿主或经用户授权的本地桥接。明确服务端浏览器与用户本地登录态的来源；设备连接、多目标选择、系统权限、断连、会话恢复和取消进入同一执行生命周期。云端不可直接完成的本地能力由实际桥接执行，不用模拟结果代替。

为目标插件的 commands、hooks、agents、apps 与客户端扩展建立明确协议映射：命令进入任务执行入口；hooks 绑定指定事件并防止重复触发；agents 继承适用任务权限和预算；apps/扩展连接所需客户端展示与事件回传。SDK 已有能力优先复用，专有接口以实际协议和目标平台证据实现，不默认互相兼容。

出口：目标插件的必要组件真正运行，浏览器/设备操作有证据，授权与取消链路一致，安装界面与实际运行能力一致。任何已登记必要组件仍缺失时，本阶段未完成。

### 阶段 6：全链路验证、部署和最终关闭（P12–P14 及全部前置项）

先跑针对性单元/集成与隔离宿主检查，再跑代表样本的完整链路：导入/安装 → 发现/加载 → 授权 → 多工具执行 → 文件交付 → 失败恢复/取消。使用 Genkit CLI 和 trace 核对真实工具调用与效果；检查跨任务/跨账号隔离、资源占用、清理和合理性能。按实际问题调整预算，不能只把每个上限调大。

修改服务端后按项目部署入口自动发布并验证数据、健康、release 和 API contract；涉及客户端协议时两端一起更新。客户端和真机验证由用户负责的部分，必须取得实际结果后才关闭对应项，不代称通过。可按阶段发布完整且健康的当前版本，但始终只有一个当前版本和一个非运行应急恢复点，不维护并行旧产品版本。

出口：全部台账项有完成证据；全部目标样本成功且保留必要边界；所有已发现阻塞清零；线上服务健康和用户端验证已记录。至此才可称“Agent 工具调用权限问题已完整修复”。

### 阶段间管理规则

顺序依赖为阶段 0 → 1 → 2 → 3 → 4 → 5 → 6；观测、回归、文档和已触及的生命周期检查贯穿每一步。阶段内可按具体依赖细分提交和部署，不要求一次提交全部实现。每次交付更新同一台账，列出已关闭、待验证、受阻项和下一步，不把部分完成改称整体完成。

遇到平台、协议或第三方条件阻塞时，先继续可独立推进的台账项，同时说明阻塞的证据和解除条件；总任务保留未完成状态。范围取舍或降级必须由用户明确决定，不能通过改验收口径消掉问题。

| 生成 XLSX/DOCX/PDF/图片后继续处理 | 下一步按同任务产物 ID 获取正确文件，修改及再次导出保留正确版本关系 |
| 技能声明需要 Shell、Browser、Computer 或 MCP | 解析具体工具依赖并连接真实宿主，不因名称匹配整包拒绝 |
| 技能包含辅助资源、Shell 入口或构建声明 | 资源与执行入口区分；目标环境可准备并完成实际调用 |
| pyproject、需要构建的 Python 依赖或 npm 安装生命周期 | 隔离安装/构建成功，锁定与校验信息完整；安装失败有恢复结果 |
| stdio MCP 插件安装、启动、调用及退出 | JSON-RPC 与诊断输出分开，超时/取消/重启均可恢复，子进程清理完成 |
| 浏览器或设备插件需要用户登录、系统权限或目标选择 | 用户入口明确，操作在授权目标实际执行；断连/拒绝/取消均有反馈 |
| hooks、commands、agents、apps、extensions 是目标插件必要组件 | 每类按真实协议执行并提供结果，单纯显示“不支持”不算修复 |
| 并发调用、读取重试、外部操作结果未知和服务重启 | 预算准确、授权不漂移、读取可恢复，副作用不重复提交 |
| 跨账号引用、失效安装版本、私网或元数据地址 | 拒绝并提供准确原因 |
| 声称完成但缺少真实工具结果或文件 | 仍提示未完成，不以放权取消交付核验 |
