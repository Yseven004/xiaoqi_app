日期：2026-10-03。状态：提示词和消息组装已接入；无上下文的纯标签交给当前模型在聊天中纯文本追问。真实模型行为、设备视觉和云端验收仍待验证。交互沿用已确认的黑白轻量风格，不使用澄清弹窗或问题面板。

## 1. 当前问题与证据

- `lib/features/capabilities/data/skill_creator_adapter.dart` 将 Creating a skill 到 Description Optimization 之间的上游指导和完整 grader 一起注入，覆盖需求访谈、评测、对照运行等多个阶段。仅替换 Claude 名称不能完成环境适配。
- 同文件截取起点跳过了上游前面的 Communicating with the user。应保留面向用户调整术语的原则，同时按阶段加载创建资源。
- `lib/pages/home_page.dart::_buildAiMessages` 将 capabilityPrompt 拼进最新 user 消息；用户只发送标签时，该消息完全变成内部指导。截图中“收到这套说明”与这种组装方式相符，但尚未抓取该设备实际请求，不能认定为唯一原因。
- 当前要求模型输出 SKILL.md 和试用文本，再从回复解析草稿。回复声称已试用，不等于执行器确实加载该版技能完成了一次运行。
- 直接聊天与云端工具路径的能力不同，提示词必须根据实际工具可用性组装，不能统一承诺文件系统、Python 或云端操作可用。

## 3. 四层上下文

1. **产品规则**：以供应商支持的 system/developer 角色承载；定义沟通方式、真实状态、保存与网络边界。由应用提供，不从附件中读取。
2. **当前阶段与可用能力**：创建或调用意图、阶段、分支、草稿 ID/版本、实际可用工具与最近结果。程序提供事实，模型不能自行标记已保存或已执行。
3. **技能指导与任务资料**：按当前阶段加载上游相关章节。选中技能优先；普通聊天先提供摘要。附件、用户技能正文和工具返回均明确标记来源，不能覆盖产品权限规则。
4. **用户消息**：保留原文；纯标签以“选择创建技能，尚未补充文字”的意图数据表达，不把内部指导伪装成用户输入。

同一套组装规则覆盖直接聊天与云端路径，但工具说明由实际运行能力决定。修改消息组装前还需检查 AiService 最终请求中的角色合并，避免重复 system 或被供应商适配器覆盖。

## 4. 产品提示词草案

以下是小栖交互层草案，不替代上游 Skill Creator 正文：

```text
你帮助用户把想法或当前对话中的重复工作变成可再次使用的技能。
先结合当前对话分支、用户选择和实际可读的资料判断目的。

当用户只选择创建技能且没有可用上下文时，在普通聊天回复里用一句简短纯文本问题询问想完成的事，可以附一个贴近场景的例子；不要输出选项面板、JSON、特殊标记或结构化澄清格式。
上下文已足够时直接推进；缺少会明显改变结果的信息时，每轮优先问一个最关键的问题。
不要把用途、触发方式、输出和边界条件当成必须逐项填写的问卷。
对低影响、可修改的细节采用合理默认值，在展示草稿效果时简短说明；涉及实质范围、权限或数据去向时询问用户。

只加载当前阶段需要的创建或评审指导。
默认向用户展示技能用途、试用结果和下一步选择；用户要求查看时再展示技能源码和技术细节。
不要主动向普通用户讲解文件名、基准测试、评分器或内部工具协议。

草稿生成后，由执行器加载该版草稿完成一次代表性试用。
只能依据真实返回的状态描述执行、失败和产物；未执行时明确说明，不能编造试用成功。
已有草稿但试用失败时保留草稿并说明原因，不把失败隐藏成普通回复。
保存由用户点击保存触发。生成完成、用户回答问题或模型声称保存都不能替代保存操作。
修改时创建新草稿版本并保留上一版。

需要 Python 且执行服务可用时自动调用，不询问执行许可。
需要联网时说明用途与域名范围，取得对应授权后执行。
工具不可用时如实说明影响；纯文字任务继续推进。
```

示例：

- 无上下文、只有创建标签 → “你想创建一个帮你做什么的技能？比如，把书本内容改写成童话。”
- 前文已明确将科普改写成儿童故事、随后选择创建 → 直接生成相应用途草稿，不重复询问用途。
- 输入“帮我做周报”，资料包含固定模板 → 先读取模板；只追问真正缺失且影响产出的信息。
- 用户只要求“语气更活泼” → 修改已有草稿，保持其他约定，再用新版本试用。

示例用于教会判断，不作为逐字固定回复。

## 5. 程序与模型的职责

沿用普通聊天消息表达澄清问题，不增加结构化 `clarification` 事件或输入区上方的问题面板。模型通过当前对话自然追问和引导，用户照常回复；聊天历史负责保留问答上下文。`draft_ready`（草稿版本）和 `trial_result`（该版本的结果与执行状态）仍可由现有 Agent 任务事件承载。

- 模型判断是否需要澄清、以普通文本提问、编写技能与总结结果；应用负责阶段、保存权限、版本对应、取消与错误状态。
- 纯标签发送也必须调用当前选中的模型；前端不预先生成问题或拦截请求。
- 试用应是独立执行调用，传入该版技能和代表性输入，返回证据；不要求新增多智能体。纯文字试用不依赖 E2B。
- 用户可见文字与草稿文件分离；输出不合规时可做一次格式修复，仍失败则保留可恢复状态，不把 Markdown 标题匹配当成保存成功。
- 沿用已确认的“直接保存 / 修改后再看”选择和默认展示开关，不新增页面。澄清只显示在聊天记录中。试用失败后的具体操作需沿用既有异常设计；如缺失，先补确认。

## 6. 实施与验收建议

第一批：修正消息角色、按阶段加载上游内容、加入简短交互规则与示例。第二批：保留普通聊天中的自然文本澄清，接通真实试用结果，移除对用户回复正文的脆弱依赖。两批均保留原聊天分支、用户文本和已保存技能。

风险：供应商角色支持不同；旧记录缺少阶段字段；新旧事件混用；提示词缩减可能丢失上游必要指导。应由统一适配层处理角色，旧记录按空值兼容，事件增加版本并保留旧读取能力，上游章节建立映射清单。回滚只切换新工作流入口，不删除既有草稿或正式版本，不静默切回能力不足的执行路径。

待执行的端到端验收：

1. 纯创建标签通过当前模型在聊天中进行简短纯文本追问；上下文充分时直接推进，附件内容不会改写系统规则。
2. 明确需求生成草稿并真实完成一次纯文字试用；失败有真实状态，不伪造结果。
3. 回答澄清、修改与取消维持正确分支及草稿版本；关闭问题不等于同意。
4. 只有保存点击产生正式版本；保存后调用和隐藏后发现正常，旧记录可读取。
5. 使用当前所选模型验证上述行为；Python 服务不可用及联网未授权时边界正确，不宣称跨模型验证已通过。
