# Recover an isolated MCP lease after API termination

Previously the API allocated a random runner lease and started the process before recording its identity. An API crash could leave the original process and workspace unreachable even while the runner retained them.

Before the startup POST, the transport now invokes a checkpoint callback with its random lease ID, random lease token and exact startup timestamp. The code execution service writes these to a separate private SQLite document, bound to the owning tenant/task hash and exact runner URL. The runner bearer token, plugin environment, source package, model messages and task presentation do not enter this document. Lease credentials do not enter the public task document or model input. Existing SQLite WAL/FULL durability applies.

Recovery runs before the existing task execution recovery. It looks only in the current tenant/task prefix and checks the stored task binding and runner URL. A process-local active lease set prevents recovery from reclaiming a live lease owned by this API process. For a prior owner, a recovery transport addresses the original lease directly: it does not POST a new startup or send any JSON-RPC tool request. Closing the original lease obtains its completion and partial artifacts; the existing recorder saves files under the original stable lease operation ID, records cleanup and acknowledges only after persistence. The private checkpoint is removed only after acknowledgment succeeds. If transport, persistence or acknowledgment fails, the identity remains available for another recovery attempt. Missing completion does not prove the original operation failed.

Tests use a real child API process that acquires a lease and exits without normal cleanup. A new service instance finds the pre-start checkpoint, stops the original lease once, preserves original bytes, and sends no tool or replacement startup request. Cross-tenant lookup and a changed runner URL do not touch it. A failed first acknowledgment retains the checkpoint; subsequent recovery saves no duplicate artifact and clears it after acknowledgment. Existing transport tests verify process-local active lease registration and removal.

Final local checks: analyzer clean, complete Dart regression 286 passed, complete runner regression 52 passed. The runtime fixture performs two cleanup requests only because the first acknowledgment deliberately fails; startup count remains one throughout. No production or device success is inferred from these local checks.

No Flutter/server public API contract change or client rebuild is required. Both server-side changes use the normal unified release deployment. Reverting the code does not erase private checkpoints or existing files; no credential migration or service purchase is involved.

This recovers an original runner lease and its files after API loss. It does not reconstruct the Genkit pending RPC future, manufacture a successful tool return, persist leases through runner restart, or remove the existing lease expiration. Those remaining P07/P13 requirements remain open. Unknown effects must not be re-executed just to obtain a result.

The preceding event-replay CI (run 40556257652) failed before deployment in its closed-channel drainage test. Joining the reader exposed two legitimate close wake markers; the poll loop now drains wake markers rather than treating one as a final message boundary. The assertion is retained, and the complete 52-test runner suite passes after the correction. This fixes the cause rather than bypassing the gate. Production stayed at the healthy 1211afc release throughout that failed build.
