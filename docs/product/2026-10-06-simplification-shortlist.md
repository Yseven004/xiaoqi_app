# 小七删减清单：先减少重复的 AI 工作路径

日期：2026-10-06。只读检查结果；尚未删除业务代码、运行测试或部署。

## 先看结论

**有明确的精简空间。第一目标是让聊天、重试、继续回答统一走一条路径，后台最终只维护 Harness 一套 Agent。**

你已确认两项使用要求：手机或平板联网即可独立使用；切换应用或锁屏后，云端任务继续，回来能查看结果。精简后仍须满足这两项要求。

“现在有两套”已在代码中确认；“两套都可以立即删到只剩一套”尚未验证。下面区分删除目标和必须完成的替代工作。

## 1. 可以直接删：本轮没有确认的项目

本轮检查到的主要问题是**仍在使用的新旧路径并存**。尚未找出足够证据，证明某个整套模块已经完全无人使用。因此目前没有可以直接删除的业务模块，也不编造可删除数量。

## 2. 优先合并、验收后删除

| 删除目标 | 删掉后少维护什么 | 删除前需要完成什么 |
|---|---|---|
| 旧的自研 Agent 循环 | 一套模型请求、工具循环和异常处理 | Harness 接管仍走旧路径的任务，包括图片兼容；正在运行的旧任务处理完毕 |
| 首页里重复的对话执行路径 | 两种消息发送、停止、重试和恢复方式 | 核对普通发送、重新生成、继续回答，统一接入同一任务入口；未登录时的体验需要明确，不能直接删成报错 |
| 旧聊天路径专用的模型转发和附件摘要代码 | 重复维护模型参数、流式回复和长文处理 | 逐个迁走调用方；标题生成、笔记分析等仍使用的能力不能随整个文件一起删掉 |
| 新旧 Agent 的分流配置 | 运行时白名单、兼容分支以及相应运维配置 | 所需模型和图片场景已接管，历史任务仍能读取，回退安排已确定 |

建议顺序：**先统一入口和遗漏的重试/续写路径，再完成 Harness 接管，最后删除旧实现及其配置。**这个顺序能避免旧代码删除后又以“补丁”形式长回来。

## 3. 先保留能力，允许以后换成更简单的实现

- **阅读、资料、笔记和已有数据。**这是小七本身的产品价值。
- **账号和文件访问控制。**保证任务与文件属于正确的用户。
- **云端任务记录、后台执行和结果保存。**支持锁屏继续、取消、重开和取回文件。
- **执行 Python 的隔离环境及文件交付。**调用这些工具时需要；不代表每次普通回答都要启动沙箱。

这里保留的是能力，不是要求现有每个文件、服务和部署方式永久保留。

## 4. 连接层还能不能大幅减少？

仍值得评估。现在的连接代码帮助 Harness 使用已有 Python 工具；直接删除会切断资料读取、草稿和 Python 执行。若用 Harness 插件替代，应比较“新插件需要维护的代码和部署”与“能删除的旧代码”，不能只看架构图少了几个方框。

本轮没有证明“一个 Harness 服务可以直接替换全部后端”。也没有把连接层判定为永久必需。是否改变云端部署方式，放在明确替代方案之后决定。

## 当前决定与下一步

这是一份删减提案，尚未确认改写未登录体验、取消模型支持或更换云服务。下一步实施前，应把四个删除目标映射到全部调用方和替代行为，形成具体改动范围；技术判断由开发侧承担，只把确实影响用户体验的选择交给你。
