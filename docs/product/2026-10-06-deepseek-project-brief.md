# 给 DeepSeek 的小七项目背景说明

整理日期：2026-10-06。以下以我的口吻说明，供继续讨论产品与架构。进度来自当前代码和项目记录；本次整理没有重新部署、运行测试或操作真机，历史验证不等于最新版本已验收。

## 1. 我是谁，以及这次真正想解决的问题

我是非技术型独立开发者，正在借助 Codex 开发“小七”Flutter 应用。项目已经有实际页面、业务代码和云端服务，不是从零开始。

我最关心的是：这套产品能否由我长期维护和运转。现在接入链路、部署配置、运行时、任务状态和故障排查涉及的环节越来越多，我认为已经超出了自己能够轻松掌握的程度。

请把“减少我必须维护的代码、服务和配置，出了问题容易定位和恢复”作为方案的重要约束。我们正在重新讨论简化方向，尚未决定推倒重写、迁移到手机本地运行，或者更换云基础设施。

## 2. 小七是什么产品

小七的方向是阅读与学习应用，先做好阅读空间，再逐步扩展学习空间，二者尽量共用底层能力。

- 阅读空间：围绕书籍和资料组织阅读、批注、笔记，以及 AI 阅读辅助。
- 学习空间：未来逐步扩展讲解、学习任务、练习和复习；不能把这些规划当作全部已经完成。
- AI 应当结合用户的书籍、附件和阅读上下文做事，包括分析资料、整理内容，以及在需要时调用工具生成真实文件。
- Agent 是产品能力的一部分。仅能聊天或返回一段需要用户自行运行的代码，不满足“实际执行并交付结果”的要求。

目前云端 Agent 迁移按个人账号白名单试用推进，还不是面向大量用户的正式运营状态；这也不意味着产品长期只服务一个人。

## 3. 已有产品和代码基础

前端是 Flutter / Dart，目前重点在 Android 手机和平板场景。仓库还有其他平台目录，但这不代表这些平台都已验证。

已有代码覆盖：书库与书籍资料、PDF/EPUB/DOCX/网页等资料处理、拍摄与识别、页面阅读和批注、笔记编辑、AI 对话、附件、会话历史、模型选择，以及技能相关入口和数据处理。上述是已有代码范围，不表示所有格式和流程都已通过最终验收。

本地已有 SQLite 业务存储，并有 XiaoqiDocument 文档模型。书籍、笔记、资料关联等产品数据需要延续，不能简单用 Harness 的会话历史替代。架构图里的 BookContentPackage 应先按设计概念理解，本次核对没有确认它已完整落地。

最近还做过一次界面范围收缩：底部“笔记”“我的”保留入口但显示静态空状态；书籍详情移除了独立正文工作台入口。资料预览、最近笔记和主界面笔记能力保留，没有清除历史笔记数据。这项修改记录为代码完成、待用户验证。因此不要根据旧图或代码文件名，默认所有旧入口仍在使用。

## 4. 关键事实：我们已经接入过 DeepSeek Harness

我们并非还停在“Flutter 能不能接 Harness”的讨论阶段。此前已经决定复用官方 Harness，逐步替换自研 Agent 循环，并做了实际集成和一条云端验证。

当前集成结构大致是：

```text
Flutter 小七客户端
    ↓
Python 业务 API（阿里云函数计算 FC）
    身份鉴权、任务创建、状态/事件查询、文件下载
    ↓
Python Worker（阿里云 FC）
    任务归属、租约、运行时生命周期、取消、产物交付
    ↓
官方 ACP Python SDK → DeepSeek Harness 运行时
    ↓
绑定本机地址的 HTTP MCP 工具桥
    ↓
已有小七工具 / 阿里云 Agent Sandbox 的 E2B 兼容接口
    ↓
OSS 文件存储 + Tablestore（OTS）任务与元数据
```

这里的 MCP 桥绑定运行环境内的本机地址，不是额外对公网开放的 MCP 服务。E2B 在当前链路中是访问阿里云 Agent Sandbox 的 SDK/兼容接口，不能据此直接认定我们同时运营两家独立沙箱服务。

Harness 已接入的工具桥包括：

| 工具 | 用途 |
|---|---|
| `read_task_material` | 按需分段读取任务资料 |
| `read_skill_resource` | 读取技能资源 |
| `draft_workspace` | 处理工作区草稿 |
| `execute_python` | 在沙箱中执行 Python 并返回产物 |

当前实现显式限制 Harness 的默认工具，主要通过上述小七工具桥执行。它不是把官方全部内置工具、技能、终端和子 Agent 能力直接开放给用户。App 里的通用“MCP 连接器”入口尚未开放，不能与内部已使用 MCP 混为一谈。

旧自研运行时仍保留用于兼容和回退。任务记录中的 runtime 决定走 Harness 还是旧路径；记录中的 Harness 白名单仅包含个人账号。普通聊天、模型/图片兼容路径也还没有完全统一。

此前采用 ACP 的理由是会话恢复和单会话取消需求；不是随意增加协议层。实际发行组合采用固定版本，下载研究的官方源码版本与已部署发行包并不相同，不能混装。具体是否还应保留这套跨语言连接方式，正是可以重新评估的部分。

## 5. 到底做到哪一步了

| 项目 | 有证据支持的状态 |
|---|---|
| 官方运行时接入 | 已有 Harness worker、ACP 接入、MCP 工具桥和任务路由代码；本次也核对到相应实现 |
| 云端基础链路 | 2026-10-05 项目记录记载 API/Worker 已有部署，个人白名单已启用 |
| Python → CSV | 历史云端 smoke 记录为成功：Harness 调用 Python，生成 CSV，下载后核对内容为 `2+2,4`；这是单条链路验证 |
| 后端自动化检查 | 历史记录包含隔离环境下 37 项测试及 3 个子测试通过；覆盖中包含模拟，不等于全部真实云端场景通过 |
| 最新 App 完整闭环 | 尚不能称为完成：后续代码修改、部署版本核对、真实取消/恢复及目标设备验收仍有缺口 |

近期完成或修正的代码包括：个人账号从首页直接创建 Agent 任务，不要求先保存/选择技能；附件和技能资料分段读取；回复下返回文件及系统保存；停止后等待云端终态；重新打开会话恢复原任务与结果。

邮箱验证码登录和登录门禁已有实现，方向是个人邮箱授权，不再要求新用户手动配对。但项目记录对 SMTP 配置、最新 API 发布和真机验收仍有未完成项，不能把邮箱登录的完整线上链路说成已通过。

阶段 3 的停止确认、清理重试、会话重开恢复，以及最近的 PDF 修正，记录明确写了“代码已接入/修正，待验收”。之前通过的测试不能替这些更新背书。

## 6. 最近遇到的实际问题

1. **App 入口与真实执行不一致。** 用户录屏中曾出现请求 Python/CSV 后只收到代码和“自行在终端运行”的说明，没有看到 App 内真实执行与文件交付。这说明云端 smoke 成功不等于 App 闭环已打通；之后已修改首页入口，仍需复测。
2. **大 PDF 上下文处理。** 旧代码把 PDF 全文重复塞进对话和历史，出现上下文溢出。最近改为附件 ID 引用、按需分段读取；宽泛总结要求覆盖全文后整合。另一个直连路径的“空摘要”问题尚未确认独立根因，不能混称为全部修好。
3. **取消与恢复跨越多层。** App 显示停止，还需要确认 Harness 停止、外部沙箱清理、云端任务终态和重新进入后的显示一致。相关修正已有代码，真实端到端验收仍未完成。
4. **部署和依赖维护负担。** 已处理过内部令牌不匹配、子进程模块路径、Windows 打包 Linux 启动脚本换行、E2B 版本与云接口不兼容等问题；另外还记录有发布版普通聊天备用代理失效。这些是我担心长期维护的具体原因。

请不要只建议“再加一个 SDK”就能解决这些问题，也不要把所有现有层都默认视为必须保留。需要判断每一层到底在承担必要业务责任，还是可以被官方能力或更简单的部署方式替代。

## 7. 我认可的原则与仍在讨论的选择

我倾向于：小七保留自身的阅读、资料、笔记和用户体验；通用 Agent 循环、工具调度等尽量复用 Harness；优先用配置、Profile、插件或 Skill 扩展，减少修改官方核心源码；执行代码时保留必要隔离。

但这些是方向，不代表图片中的每个方框都必须做成独立模块或服务，也不代表现有实现就是最终答案。当前还未确定是否应继续使用 Python Worker + ACP + MCP，是否换成更直接的服务封装，以及是否值得采用 Android 内嵌运行时。

我给出的参考项目是：
https://github.com/zmm863-commits/paopaocat-deepseek-harness-mobile

它自述使用 Flutter + Android 内嵌 Node/Harness，与我们目前的云端执行方式不同。请把它作为研究参考，而不是已经完成源码审计、可直接复用且验证稳定的底座。请核实公开代码、许可、构建材料与实际能力之后再判断。

## 8. 我希望你下一步帮我判断什么

请先基于上述真实背景讨论，暂时不要直接生成代码或扩展新功能。

1. 现有链路中，哪些复杂度确实来自我们的产品要求，哪些来自当前实现选择，可以删除或合并？
2. 对一个非技术型独立开发者，继续精简当前云端方案、更直接地服务化 Harness、参考 Android 内嵌路线，分别要实际维护什么？先给有依据的倾向，再说明不确定项。
3. 如果更换方案，哪些现有页面、资料、笔记和代码能保留？哪些代码或服务可以明确退役？不要只新增一套体系而保留所有旧负担。
4. 请用一条真实阅读任务说明最小闭环：导入资料 → 提问/分析 → 工具执行（需要时）→ 保存/交付结果 → 失败、取消与重开恢复；指出需要验证的环节。
5. 先推荐一个范围小、可撤回的验证步骤。技术建议请依据官方文档和可检查的源码，区分已知事实、推断和待验证项；不要把“连接 DeepSeek 模型 API”等同于“完整接入 Harness”。

最重要的问题是：在保留小七核心体验与已有数据的前提下，怎样真正降低长期维护成本？
